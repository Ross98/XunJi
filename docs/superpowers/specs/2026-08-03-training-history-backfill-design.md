# 动作追踪全历史数据补全设计

## 目标

动作追踪图表按所选动作显示其全部已记录训练日，而非只限训练页当前预取的 14 天。历史数据从训练页后台逐日补全，页面请求不等待完整扫描。

## 范围

- 在访问 `/training` 时启动或复用一个全局历史补全任务。
- 从今天向前扫描最多 730 天。
- 仅请求 SQLite 缓存中不存在的 `training:<date>:True` 数据；已有空响应和有训练响应均跳过。
- 每个未缓存日期完成请求后等待 6 秒；请求严格串行。
- API 已有的 429 重试逻辑继续生效。单日请求失败时记录并继续下一个日期，不写入失败响应缓存。
- 图表接口继续从全部已缓存且非空训练日期读取数据，因此刷新训练页后自动包含新补全日期。

## 数据流

1. 用户打开训练页，页面照常预取最近 14 天并立即渲染。
2. 路由确保后台补全任务正在运行；若已有任务，则不重复创建。
3. 任务从今天向前检查 730 天的 `True` 缓存键。
4. 缺失键通过 `DataService.get_training(date, full=True)` 获取，完成后等待 6 秒。
5. 训练追踪接口读取缓存中全部有训练记录的日期。用户刷新页面或重新打开动作追踪时看到补齐数据。

## 容错与恢复

- 服务重启会取消内存中的任务，但已完成日期保留在 SQLite 缓存；下次访问训练页自动跳过这些日期并继续。
- 同一进程只允许一个补全任务，避免并发请求触发限流。
- 单日网络或上游错误不影响训练页响应，也不阻断后续日期。

## 验证

- 单元测试：任务跳过已有缓存、仅查询缺失日期、按串行节奏工作。
- 单元测试：动作追踪接口从缓存所有非空训练日期生成历史数据。
- 全套 pytest 通过。
